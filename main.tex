\begin{abstract}
Serverless functions backed by SQLite face a persistent cold-start bottleneck: after an idle period the OS page cache is evicted, and the first query runs two to three orders of magnitude slower than subsequent ones. Prefetching is the natural remedy, and existing work evaluates it by post-prefetch first-query latency. We show that this metric can misrank strategies, because in a serverless request the prefetch itself sits on the user-visible critical path. We introduce a critical-path cost accounting that decomposes cold-start latency into a cold file open, per-page delivery, and the first query, and evaluates it under two deployment boundaries: an integrated warm-process model that reuses an open handle, and an external warmer that pays the cold open. The framework uses only standard POSIX interfaces and requires no modification to SQLite, the kernel, or the runtime. Under this accounting the ranking reverses. A full working-set cache dump minimizes first-query latency (80\% to 91\% reduction) yet regresses end-to-end cold starts by roughly an order of magnitude on broad workloads, because its 0.8 to 7 ms delivery cost dominates the response. The robust operating point is frugal coverage: a set under 2 MB that covers the B+tree interior navigation path yields a 25\% to 30\% end-to-end reduction across skewed and uniform read workloads, and hot-leaf prefetching helps only under an independently verified hotspot. At matched footprint, a frequency-ranked dump is statistically indistinguishable from a type-aware selector, so footprint and coverage carry the result rather than selector sophistication. The design rule holds under write churn, memory pressure, 10× database scaling, and a moving hotspot, and the first-query effectiveness of the selected page sets carries over to a separate-host Apache OpenWhisk deployment.
\end{abstract}

\section{Introduction}\label{sec:introduction}

\subsection{Background}\label{sec:background}

\subsubsection{Serverless SQLite as a Growing Deployment Target}\label{sec:serverless-sqlite}

Serverless computing has become a dominant execution model for cloud applications, offering transparent scaling, fine-grained billing, and simplified operations. A growing share of serverless workloads is stateful and accesses persistent data in embedded databases co-located with function instances. SQLite is the most widely deployed engine for this role: Gaffney et al. \cite{Gaffney2022} estimate that over one trillion SQLite databases are in active use and identify edge computing as a key emerging use case for its zero-configuration data management. FaaS platforms such as AWS Lambda, Azure Functions, and Google Cloud Functions let functions mount persistent storage or use ephemeral local disk, making SQLite a natural choice for function-local state, configuration, and lightweight analytics. In such deployments SQLite is the storage layer of the function, and its latency contributes directly to the function's response time. Production edge databases and object-storage-backed SQLite systems ~\cite{CloudflareD1, SqliteWebVfs, Turbolite} place the same local storage layer on the request path.

\subsubsection{Warm Container, Cold Data}\label{sec:warm-container}

Wang et al. \cite{Wang2018} measured over 50,000 function instances across AWS Lambda, Azure Functions, and Google Cloud Functions and showed that platforms reuse containers or virtual machines across invocations, so a warm runtime is the common case. They also observed frequent resource contention between co-located functions. Such contention is consistent with the OS reclaiming file-backed pages between invocations, so pages cached by one invocation may no longer be resident when the next arrives. Shahrad et al. \cite{Shahrad2020} characterized production traces from Azure Functions and found that invocation frequencies span eight orders of magnitude and that inter-invocation intervals are highly variable, which makes future invocations hard to predict. Platforms therefore combine keep-alive and prewarming policies that hold the runtime warm while allowing memory to be reclaimed during idle periods. The result is the state this paper targets: the function runtime and its SQLite handle are alive, but the OS page cache backing the database file has been evicted. We refer to this state as warm container, cold data, and use the hyphenated form warm-container, cold-data as a modifier throughout.

\subsection{Motivation}\label{sec:motivation}

Container-level cold-start optimization has advanced rapidly. The histogram-based prewarming policy of Shahrad et al. \cite{Shahrad2020} raises the fraction of invocations that land on a warm container, and Catalyzer \cite{Du2020} reaches sub-millisecond function startup through checkpoint/restore and the sfork primitive. Neither technique restores the OS page cache: a checkpoint does not carry file-backed pages, and prewarming keeps the runtime alive while memory is reclaimed. As these techniques succeed, the cold-start penalty that remains sits in the data path.

That penalty is not small. On our reference database (Section~\ref{sec:refdb}), the first query after a cold OS page cache takes 503 to 1072 µs depending on the workload, against 1 to 3 µs once the cache is warm (Section~\ref{sec:workloads}), a slowdown of two to three orders of magnitude. The storage-layer penalty is therefore in the same sub-millisecond regime as container startup itself, so even an optimally warmed container leaves the data path as the dominant remaining cost.

The cost arises from a dependent fault chain. Each query walks the B+tree from root to leaf, and each missing page must be fetched before the next page address is known. On local NVMe each link costs microseconds. When SQLite is served from object storage over HTTP range requests ~\cite{SqliteWebVfs, Turbolite}, each link becomes a multi-millisecond GET and the same chain is amplified by orders of magnitude. This paper quantifies the chain at the local-storage tier and leaves the remote tier to future work (Section~\ref{sec:conclusion}).

\subsection{Challenges and Problem Statement}\label{sec:challenges}

Prefetching the pages that the first query will touch is the natural remedy for the warm-container, cold-data state. Three challenges stand in the way, and no prior approach addresses all of them at once.

\textbf{Challenge 1: Targeting.} The OS page cache operates on file blocks and has no view of SQLite's B+tree. Kernel readahead detects sequential access and misses the non-sequential root-to-leaf traversal that every query performs, whereas loading an entire working set spends I/O on pages the first query never touches. The prefetch set must be small enough to be cheap and sound enough to cover the navigation path of any first query. How to select such a set, and whether structural page-type knowledge or observed access frequency selects it better, is an open question.

\textbf{Challenge 2: Cost Accounting.} Prefetching is not free. Prior work optimizes the post-prefetch first-query latency and implicitly assumes that a lower first query yields a faster cold start. In a serverless request the user blocks on the function's response, so the time spent opening the file and issuing per-page prefetch operations extends the response directly. When this preprocessing cost exceeds the first-query reduction, prefetching slows the cold start.

\textbf{Challenge 3: Deployability.} Functions run in restricted runtimes where modifying the OS kernel, the storage firmware, or the database engine is usually infeasible. Solutions that patch SQLite \cite{VanDeBogart2009}, move transaction logic into the FTL \cite{Kang2013}, or add kernel modules \cite{Leis2023} cannot be deployed there. A practical mechanism must operate at the application layer through standard OS interfaces without privileged access.

The three challenges are coupled. A well-targeted set that ignores its own cost can be net-harmful, a cost-aware but poorly targeted set brings no benefit, and either one is moot if it cannot be deployed. This paper addresses all three together.

\subsection{Our Contributions}\label{sec:contribution}

This paper presents a non-intrusive prefetch framework for SQLite cold starts in serverless and edge deployments and, with it, a methodology for evaluating such prefetch on the user-visible critical path. Our contributions are:

\textbf{Critical-path cost accounting (Section~\ref{sec:methodology})}. We decompose cold-start latency into a cold file open, per-page delivery, and the first query, and evaluate it under two deployment boundaries: a warm-process model that reuses an open SQLite handle, and an external-warmer model that pays the cold open. We further separate page selection from page delivery so that selection accuracy is not conflated with delivery residency. To our knowledge, this is the first evaluation of SQLite cold-start prefetch that charges the prefetch itself to the critical path, and it exposes a systematic gap between first-query and end-to-end rankings.

\textbf{A frugal-coverage design rule (Sections~\ref{sec:strategy} and~\ref{sec:evaluation})}.  Charging preprocessing reverses the naive ranking. The full working-set cache dump minimizes first-query latency but regresses end-to-end cold starts by roughly an order of magnitude on broad workloads, because delivery cost dominates. The robust operating point is a set under 2 MB that covers the B+tree interior navigation path, which yields a 25\% to 30\% warm-process end-to-end reduction across skewed and uniform read workloads. Hot-leaf prefetching is a conditional add-on that helps only under an independently verified hotspot, and at matched footprint a frequency-ranked dump is statistically indistinguishable from the type-aware selector. Page-type knowledge therefore serves as an interpretable coverage guarantee that stays stable when the read hotspot moves, rather than as a uniquely faster selector. A physical layout rewriter that clusters interior pages at the file head is a negative result under our workloads.

\textbf{A deployable toolchain and its validation (Sections~\ref{sec:deployment},~\ref{sec:eval-robustness}, and \ref{sec:eval-portability}).} The framework uses only standard POSIX interfaces (mmap, mincore, madvise) and modifies neither SQLite, the kernel, the storage firmware, nor the serverless runtime. We validate the design rule across six robustness axes on a controlled workstation: write churn, memory pressure, multi-process cache sharing, workload instantiation, database scaling, and a moving read hotspot. We then deploy the same toolchain on a separate-host Apache OpenWhisk runtime, where every strategy that is strongly effective on the workstation remains effective and per-cell first-query effectiveness ranks correlate at Spearman $\rho$ of 0.76 to 0.81.

\textbf{Scope of evidence.} The workstation is the sole basis for the end-to-end cost accounting and the design rule. There we measure the first-query, delivery, and cold-open terms directly and instantiate the two deployment boundaries as models of serverless keep-alive behavior rather than as traces from a commercial platform. The OpenWhisk deployment measures deployability and relative first-query effectiveness only, so it establishes neither cross-platform end-to-end ranking nor absolute-latency or hardware portability. We do not measure commercial FaaS providers, other hardware classes, or the remote object-storage tier, for which we claim only that the same dependent fault chain motivates analogous accounting. Section 8 discusses these limitations further.

Section~\ref{sec:related} surveys related work. Section~\ref{sec:fundamentals} reviews SQLite's B+tree layout and defines the warm-container, cold-data measurement model. Section~\ref{sec:methodology} presents the cost model, the selection–delivery decomposition, and the measurement and statistical protocol. Section~\ref{sec:strategy} describes the prefetch strategies and physical layouts. Section~\ref{sec:setup} describes the platform, reference database, and workloads. Section~\ref{sec:evaluation} reports results, Section~\ref{sec:discussion} discusses limitations, and Section~\ref{sec:conclusion} concludes.

\section{Related Work}\label{sec:related}

Table~\ref{tab:capability} positions this work against prior art along three axes: structural targeting of B+tree pages, cost accounting of the prefetch on the critical path, and non-intrusive deployment. No surveyed system provides all three, and the cost-accounting column is empty throughout.

\subsection{OS-Level and Application-Directed Prefetching}\label{sec:os-prefetch}

OS prefetching begins with Smith~\cite{Smith1978}, whose one-block lookahead exploits sequential access and includes a cost model for when to prefetch. Anticipatory scheduling~\cite{Iyer2001} addresses deceptive idleness by waiting briefly for the next nearby request. Both trade time for locality because the OS lacks application semantics, and both assume seek-dominated disks, a premise that does not hold on NVMe. Our cold start also has no access history for the first query, so we deduce the required pages from the B+tree structure instead of predicting them. libprefetch ~\cite{VanDeBogart2009} closes the semantic gap by letting the application declare future reads so the OS can issue them in C-LOOK order, accelerating SQLite table scans by up to 20× on HDDs. Its gains come from seek avoidance with reorder buffers of hundreds of megabytes, and its SQLite integration modifies roughly 500 lines of engine source. In our regime the bottleneck is per-page cache-miss and syscall cost rather than seek time, so every prefetched page extends the critical path and frugality replaces volume. Section~\ref{sec:eval-attribution} reproduces libprefetch's ordering effect as a delivery-order arm and finds its NVMe residue confined to the synchronous delivery term.

\subsection{Buffer-Pool Warming and Learned Prefetching}\label{sec:buffer-warming}

Buffer management was formalized by Effelsberg and Härder~\cite{Effelsberg1984}. Learned prefetchers build on it: Chen et al.~\cite{Chen2021} cast page prediction as classification and report 76\% to 87\% precision and recall, but evaluate prediction accuracy rather than end-to-end latency, quantify neither inference overhead nor mis-prefetch cost, and train on warm-start traces that a cold cache does not provide. Pre-Buffer~\cite{Yi2026} targets hit-rate collapse when hotspots shift by predicting the next cycle's hot set from per-cycle records, loaded by a background thread. It faults Chen et al. for ignoring prefetch overhead, yet measures only hit-rate recovery and total execution time, and its background thread keeps that overhead off the user-facing path. In a serverless cold start the prefetch runs on the critical path before the first query, which is what makes syscall-level cost accounting necessary. Leaper~\cite{Yang2020}, a learned LSM prefetcher, depends on access skew, consistent with our finding that hotspot-based selection helps only when a hotspot exists. Funke et al.~\cite{Funke2022} show in query compilation that preprocessing latency can dominate short-query response and that a lightweight mechanism beats a heavy one below a break-even point, the same critical-path lesson we draw in the I/O domain. Section~\ref{sec:eval-attribution} ports the selection cores of the InnoDB buffer-pool dump and of Pre-Buffer as competitive baselines and evaluates a learned transition model in the lineage of Chen et al. under the same accounting.

\subsection{SQLite Storage: mmap and the Write Path}\label{sec:write-path}

Crotty et al.~\cite{Crotty2022} argue against \texttt{mmap} as a buffer-pool replacement but exempt read-only workloads whose working set fits in memory. Our use sits in that exception and is narrower still: SQLite's pager retains caching and recovery, and we use ~\texttt{mmap}, ~\texttt{mincore}, and \texttt{madvise} only as a prefetch-hint channel. vmcache~\cite{Leis2023} retains DBMS-controlled eviction through \texttt{madvise} but finds that Linux page-table primitives do not scale at high frequency and adds a kernel module. We occupy the opposite corner, about 92 \texttt{madvise} calls per cold start, unprivileged and application-layer, where standard interfaces suffice. A separate strand optimizes SQLite's write path in mobile and embedded settings through engine, journaling, or flash translation layer (FTL) changes~\cite{Jeong2013, Kang2013, Kim2012, Oh2015}. All require invasive modification and target write amplification, which is orthogonal to read cold start. Gaffney et al.~\cite{Gaffney2022}, the most comprehensive SQLite evaluation, prewarm every table before measurement and thus treat cold start as noise to remove rather than a cost to measure.

\subsection{Serverless Cold Start and SQLite at the Edge}\label{sec:serverless-coldstart}

Serverless cold start is characterized at the platform level by container reuse~\cite{Wang2018} and unpredictable invocation intervals~\cite{Shahrad2020}, which together produce the warm-container, cold-data state of Section~\ref{sec:warm-container}. Catalyzer~\cite{Du2020} reaches sub-millisecond startup through checkpoint/restore, but it does not restore the OS page cache. At the storage layer, SQLite increasingly runs from edge and object-storage backends~\cite{CloudflareD1,SqliteWebVfs,Litestream,SqlJsHttpvfs,Turbolite}, where a custom VFS turns each page I/O into an HTTP range request and cold start becomes the headline metric~\cite{Turbolite}. Closest to our selection lever is the .dbi helper of sqlite\_web\_vfs ~\cite{SqliteWebVfs}, which gathers navigation-critical interior and metadata pages into a sidecar that the VFS prefetches, validating interior-first selection in production. It is a sidecar for a read-only HTTP VFS, publishes no accounting of the prefetch cost, and stops at page types. We operate on the local OS page cache, add no file, support read-write workloads, charge the prefetch to the critical path, and additionally evaluate an access-frequency leaf lever. Section~\ref{sec:eval-attribution} returns to .dbi's copy-rather-than-reorder design when discussing our layout rewriter.

\section{SQLite Cold-Start Fundamentals}\label{sec:fundamentals}

\subsection{B+tree Storage and Page Types}\label{sec:btree}

SQLite stores a database in a single file of fixed-size pages, 4 KB in our configuration, and each table and index is a B+tree over those pages~\cite{Gaffney2022}. Interior pages hold keys and child pointers, and leaf pages hold row data or index entries. Page 1 holds the file header and the root of the \texttt{sqlite\_master} schema tree, and the root page of each user table or index is recorded in the \texttt{rootpage} column of \texttt{sqlite\_master} and is usually a low page number. Our reference database of 600,000 rows (Section~\ref{sec:refdb}) occupies about 103 MiB and contains 92 interior pages, 51 in the table B+tree and 41 in the secondary index, totaling 368 KB, plus 26,239 leaf pages.

Standard B+tree fanout makes interior pages 0.35\% of the file, yet every query traverses them from root to leaf. A single point query touches only the pages on one root-to-leaf path, typically three to four including the leaf, whereas a workload's accumulated interior set converges to all 92. This distinction separates two prefetch targets: a per-query path of a few pages and a workload-wide interior skeleton of 368 KB. Both are small, and both lie on the navigation path that no query can skip. This arithmetic is a direct consequence of B+tree fanout rather than a property specific to SQLite, and it is what makes a frugal prefetch set possible.

\subsection{Cold-Start Mechanics}\label{sec:coldstart-mechanics}

With an empty OS page cache, the first query must fetch every page on its root-to-leaf path from disk, one dependent fault at a time, because each child pointer is unknown until its parent page is resident. On commodity NVMe each fault costs 5 to 100 µs, and the chain sums to the cold first-query latencies of 503 to 1072 µs reported in Section~\ref{sec:workloads}, two to three orders of magnitude above the warm case. The interior pages on that chain are few and known in advance (Section~\ref{sec:btree}), so a prefetch that makes them resident before the first query removes the interior faults. Whether this improves the end-to-end cold start depends on which pages are selected (Section~\ref{sec:strategy}) and on what the prefetch itself costs (Section~\ref{sec:methodology}).

\subsection{The Warm-Container, Cold-Data Measurement Model}\label{sec:measurement-model}

Our measurement model instantiates the warm-container, cold-data state of Section~\ref{sec:warm-container}. Before each measurement we keep the process-layer state warm, namely the SQLite handle, prepared statements, and the mmap mapping, and clear every software cache below the process layer. Table~\ref{tab:measurement-model} lists the state of each layer at measurement time and the serverless condition it models.

This design is deliberate on three counts. It matches deployments that reuse containers, where the runtime and handle survive and only the page cache must be re-established. It isolates the variable under study, since SQLite parser and optimizer startup is a constant that no prefetch strategy changes. And it reduces variance, because a fresh process per measurement adds 50 to 200 µs of initialization noise that would require more repetitions to suppress. The one bias the model introduces is a warm CPU cache and TLB, which we estimate at 1 to 3 µs, below 1\% of the cold baseline. Section~\ref{sec:protocol} gives the operational protocol, including cache clearing, residency verification, and cell rejection.

\section{Cold-Start Cost Model and Measurement Methodology}\label{sec:methodology}

\subsection{The End-to-End Cost Model}\label{sec:cost-model}

The first-query latency $t_{\text{fq}}$ measures only the SQL query's wall-clock time and excludes the cost of issuing the prefetch. From the user's perspective the relevant quantity is the time from function wake-up to query completion, and in a serverless request every microsecond of prefetch preprocessing lands on that path. We decompose the preprocessing into two syscall-level terms. The cold-open cost $t_{\text{open}}$ is the cost of opening the database file with a cold cache. It is constant for a given layout and independent of the prefetch strategy, about 179 µs on our platform (Section~\ref{sec:eval-tradeoff}). The delivery cost $t_{\text{deliver}}$ is the cost of issuing the prefetch operations, whether asynchronous madvise hints or synchronous pread calls, and scales linearly with the number of pages in the prefetch set. The warmer reports both terms separately.

Two deployment models follow, differing only in whether $t_{\text{open}}$ is paid:

\begin{equation}\label{eq:e2e_ext}
    \text{e2e}_{\text{ext}} = t_{\text{open}} + t_{\text{deliver}} + t_{\text{fq}}
\end{equation}

\begin{equation}\label{eq:e2e_warm}
    \text{e2e}_{\text{warm}} = t_{\text{deliver}} + t_{\text{fq}}
\end{equation}

The external-warmer model (Eq.~\ref{eq:e2e_ext}) corresponds to a separate process, such as a sidecar, that prefetches on every invocation and must open the database file itself. It is the pessimistic bound. The warm-process model (Eq.~\ref{eq:e2e_warm}) corresponds to the warm-container, cold-data state of Section~\ref{sec:warm-container}: the application is running, its SQLite handle is open, and the prefetch reuses that handle. This is the model we advocate for serverless keep-alive and edge-worker deployments. The baseline in both models is$t_{\text{fq}}$ with no prefetch, measured through the handle opened before cache clearing, so it contains no open cost and is identical across models.

The prefetch set itself is computed offline by a separate pipeline (a cold clear, a workload warmup, and a mincore snapshot) and reused across many cold starts. Its cost is amortized and does not enter the per-event critical path. Section~\ref{sec:eval-robustness} shows that under a stationary read hotspot the set does not decay across 50,000 write mutations, whereas a moving hotspot does require refreshing a frequency-based plan.

The trade-off follows directly: prefetch helps when $t_{\text{deliver}}$ is small relative to the first-query reduction and hurts when $t_{\text{deliver}}$ dominates. Section~\ref{sec:eval-tradeoff} quantifies both cases.

\subsection{Selection--Delivery Decomposition}\label{sec:selection-delivery}

The \texttt{madvise(MADV\_WILLNEED)} hint is asynchronous. The kernel records the hint, starts background readahead, and returns, so whether a page is resident when the first query runs depends on scheduling and I/O completion. The first-query latency under asynchronous hints therefore conflates two factors: whether the selected set is the right one (\textit{selection}) and how much of it is resident in time (\textit{delivery}). We separate them by running every prefetch set under the two delivery modes in Table~\ref{tab:delivery-modes}. Synchronous pread returns only after all pages are resident and gives $t_{\text{fq,pread}}$, the lower bound a perfectly delivered set can reach. Asynchronous hints give $t_{\text{fq}}$,async together with the delivery rate observed via mincore. Their gap is the delivery loss:

\begin{equation}\label{eq:delivery_loss}
    \text{delivery\_loss} = t_{\text{fq,async}} - t_{\text{fq,pread}}
\end{equation}

The synchronous mode is not a deployable strategy, since its blocking transfer adds millisecond-scale preprocessing, and serves only as a bound. Our evaluation reports the asynchronous mode as the deployable baseline. Mechanisms between the two, such as issuing hints earlier in the function lifecycle,  \texttt{readahead(2)}, or \texttt{io\_uring}, can move delivery toward the bound and are outside our scope.

Two details of the asynchronous path affect the measurements. First, the kernel readahead window (\texttt{read\_ahead\_kb} = 128 on our platform) caps a single range hint at roughly 64 pages, and on the default layout we observe only 32 of 92 requested interior pages delivered from one range hint. All per-page strategies in Section~\ref{sec:strategy} issue one hint per page and are unaffected. We keep \texttt{read\_ahead\_kb} at its default, record it with every run, and do not sweep it. Second, the harness times the first query immediately after the hints are issued. To test whether this understates delivery, we inserted sleeps of 5, 20, and 50 ms between hint dispatch and the first query for three representative strategies on two workloads (Section~\ref{sec:workloads}). The prefetch set is already fully resident at zero sleep, and the gap of Eq.~\ref{eq:delivery_loss} on the skewed workload is unchanged across sleep durations, with identical major-fault counts in both modes. The gap is therefore a persistent cost difference rather than a timing artifact. Its cause is a conjecture: synchronous reads may warm the kernel's readahead state more than one-shot hints, and confirming this would require root access to sweep \texttt{read\_ahead\_kb}, which our environment lacks.

\subsection{Measurement Protocol}\label{sec:protocol}

All measurements run on bare-metal hardware (Section~\ref{sec:setup}), and every reported cell has \texttt{majflt} $>0$, so results reflect physical disk I/O rather than simulated timing. Table~\ref{tab:protocol-phases} lists the phases the harness executes for each cell.

Three rules keep cells clean. First, residency is verified with \texttt{mincore} twice: after cache clearing, to confirm the cold state, and after prefetch, to record the delivery rate the first query actually sees. Second, any cell whose post-clear residency exceeds 1\% is excluded from aggregates, and across the cells reported in Section~\ref{sec:evaluation} the post-clear residency is 0\%. Third, the post-prefetch check runs inside the harness at microsecond granularity rather than through an external utility, whose roughly 100 ms overhead would let asynchronous readahead complete more pages and inflate the observed delivery rate.

For reproducibility we record with every run the kernel version, disk, \texttt{read\_ahead\_kb}, CPU governor and EPP mode, and load average. CPU frequency is pinned through EPP performance mode, and we verified that it reaches its maximum before each timed measurement. Each prefetch set is frozen by checksum and verified by the harness before use, so selection is deterministic across runs.

\subsection{Statistical Methodology}\label{sec:stats}
Each (workload, layout, strategy, delivery mode) cell is repeated 10 times in rep-major order, so all repetitions of a cell run consecutively and cross-cell environmental drift is minimized. We report the per-cell median, which is more robust than the mean to the long tails of cold-start latency. Because the terms of Eqs.~\ref{eq:e2e_ext} and ~\ref{eq:e2e_warm} are additive within one repetition, we compute each end-to-end value per repetition, pairing that repetition's $t_{\text{deliver}}$ and $t_{\text{fq}}$ from the same cold event, and report the median of the ten per-repetition values rather than a sum of per-term medians. Where tables or stacked figures show individual terms, those per-term medians are for attribution and may differ slightly from the end-to-end median, since the median is not additive. We also report the 95th percentile and standard deviation where relevant. Every improvement percentage is a paired comparison against the baseline from the same batch, which removes cross-batch absolute drift from the effect size.

The effects we report are large relative to per-repetition noise: first-query improvements range from 30\% to 90\%, and end-to-end differences between strategies span an order of magnitude. We therefore do not rely on marginal significance for headline conclusions, and where differences fall within the noise floor we do not rank. For example, the first-query latency of the full cache dump (Section~\ref{sec:strategy}) differs by under 3 \textmu s across the three layouts, so we call it layout-agnostic rather than rank the layouts.

To test whether conclusions hold beyond a single workload instantiation, we run a 10-seed sensitivity analysis. For each of the three read workloads (Section~\ref{sec:workloads}) we generate 10 independent instantiations of the query stream with the same database and operation count and run the full matrix on each. The per-seed effect of a strategy is its percentage improvement over the paired baseline within that seed, which cancels cross-seed machine drift. We report a bootstrap 95\% confidence interval for the mean effect from 10,000 percentile-method resamples and, as a distribution-free cross-check, the sign consistency, that is, the number of seeds in which the strategy improves. Nine or more agreeing seeds correspond approximately to a sign test at $p < 0.05$. Because a percentile bootstrap with n = 10 may under-cover at the tails, we classify effects by both criteria: robust if the CI excludes zero, directional if the CI crosses zero but at least 7 of 10 seeds agree in sign, and tie otherwise. Section~\ref{sec:evaluation} uses these three labels throughout.

The full cache dump also serves as a stability anchor, because it loads the entire resident working set and its first-query latency does not depend on which key is queried first. Across the 10-seed sweep it stays within 125.9 to 130.2 \textmu s, indicating no CPU throttling and confirming that cross-seed variation comes from workload sampling rather than machine drift. When a single-workload point estimate and the cross-seed CI disagree, we defer to the cross-seed CI.

\section{Prefetch Strategy Design}\label{sec:strategy}

\subsection{Two Selection Levers: Interior Skeleton and Conditional Leaf Bonus}\label{sec:dual-lever}

After cache clearing and before the first query, the framework issues \texttt{madvise(MADV\_WILLNEED)} hints for a selected prefetch set. Delivery is orthogonal to selection (Section~\ref{sec:selection-delivery}), so the strategies differ only in which pages they select. We organize them around two independent levers, and Table~\ref{tab:strategies} defines the concrete strategies.

The page-type lever exploits the invariant of Section~\ref{sec:btree}: interior pages are few, total 368 KB, and lie on the root-to-leaf path that every query traverses. Instead of predicting future accesses, this lever deduces that any query needs the interior navigation path and covers it. It has two forms. \texttt{Skel\-N} takes the first \texttt{N} interior pages by file offset and is purely structural, requiring no access observation. \texttt{Skel} takes the interior pages that are resident after a workload warmup, observed through \texttt{mincore}, and therefore covers only the part of the skeleton the workload actually navigates, for example 4 pages instead of 92 on the tail-boundary workload of Section~\ref{sec:workloads}. Skel observes residency but does not rank by frequency.

One caveat applies to \texttt{Skel\-N}. "First $N$ by offset" equals "top $N$ levels of the tree" only when interior pages are physically clustered at the file head, as in the Clustered layout of Section~\ref{sec:layout}. Under the default layout, where interior and leaf pages interleave, \texttt{Skel\-N} takes the earliest $N$ interior pages in the file, which may bear no relation to tree depth. This explains its workload-dependent behavior in Section~\ref{sec:evaluation}.

The access-frequency lever adds the leaves a workload touches most. After a warmup pass we count per-page accesses and take the top $K$ leaves. \texttt{Skel+K} is the union of \texttt{Skel} and these $K$ leaves, combining structural coverage with workload-specific hot data. We sweep $K$ in {10, 50, 100, 500}. Larger $K$ lowers first-query latency but raises delivery cost, so the sweep itself exposes the trade-off of Section~\ref{sec:cost-model}.

The two levers are complementary. Page-type coverage serves uniform workloads with no natural hot set, whereas access-frequency selection adds gains only where a few leaves dominate. Dump, the full resident working set after warmup, is the contrasting extreme: an application-layer analogue of InnoDB's buffer-pool dump and load, about 4,400 pages (17.7 MB) on the two 100K-key workloads and 1.8 MB on the tail-boundary workload. It is the prefetch-everything baseline against which the frugal strategies are compared.

All observation-based sets (\texttt{Skel, Skel+K, Dump}) come from the offline pipeline of Section~\ref{sec:cost-model}.

\subsection{Physical Layout Rewriting}\label{sec:layout}

Whether a range hint can cover several interior pages in one I/O depends on where those pages sit in the file. We evaluate three layouts with identical logical content. \texttt{Default} is produced by ordinary inserts and interleaves interior and leaf pages throughout the file. \texttt{Vacuum} is produced by SQLite's \texttt{VACUUM}, which rewrites the file in insertion order without regard to page type. \texttt{Clustered} is produced by our binary-level rewriter, which relocates all 92 interior pages to pages 2 through 93, follows them with the leaf pages, and appends freelist and overflow pages at the end. The rewriter patches every affected cross-page pointer (interior child pointers, overflow next-page pointers, freelist trunk pointers, and the freelist pointer in the page 1 header), emits SQL to update the \texttt{rootpage} column of \texttt{sqlite\_master}, and passes \texttt{PRAGMA integrity\_check} on the result.

We quantify interior dispersion with a scatter score, a normalized measure of how widely the interior pages spread across the file, where 0 is perfect clustering. Default scores 0.96, Vacuum 1.13, and Clustered 0.0001. VACUUM therefore leaves the layout slightly more fragmented while shrinking the file by about 3\%, so it is not a remedy for interior scattering. Figure~\ref{fig:layout-distribution} shows the three distributions: Clustered confines all interior pages to the first 400 KB, so a single range hint can cover the entire skeleton.

Clustering has a cost as well as a benefit. Moving interior pages to the file head pushes leaf pages to higher offsets, which raises the no-prefetch baseline for workloads dominated by cold leaf faults. Section~\ref{sec:eval-attribution} evaluates this trade-off and finds Clustered a negative result under our workloads. Default is therefore the layout we recommend, and it is the layout used in every experiment other than the layout comparison itself.

\subsection{Deployment Integration}\label{sec:deployment}

The two deployment models of Section~\ref{sec:cost-model} correspond to two integration points. The external-warmer model runs the prefetcher as a separate process, typically a sidecar, that opens the database file itself and therefore pays \texttt{t\_open} on every invocation (Eq.~\ref{eq:e2e_ext}). The warm-process model issues the hints from the application after its SQLite handle is open and before it serves the first request, reusing the handle (Eq.~\ref{eq:e2e_warm}). We advocate the latter for serverless keep-alive and edge-worker deployments, where the runtime stays resident across invocations.

When several processes on one node share a database file, for example multiple function instances, a single prefetch can serve all of them. With \texttt{PRAGMA mmap\_size} set to the file size, SQLite maps the file with \texttt{mmap(MAP\_SHARED)}, so pages one process brings into the OS page cache are visible to every process sharing the mapping. A private-cache configuration, in which each process reads through its own buffer with \texttt{read()}, serves as the baseline. Section~\ref{sec:eval-robustness} evaluates the shared cache together with the trade-off between re-warm cadence and freshness.

\section{Experimental Setup}\label{sec:setup}

\subsection{Platform}\label{sec:platform}

All experiments run on a single bare-metal commodity machine: an AMD Ryzen 9950X CPU with 64 GB of physical memory (62 GiB available) and a KINGSTON SKC3000D2048G (2 TB, NVMe Gen4 $\times$4) SSD. The operating system is Linux kernel 6.17. The kernel readahead window, \texttt{read\_ahead\_kb}, is fixed at its system default of 128 KB. We do not sweep this parameter (see Section~\ref{sec:selection-delivery}). Frequency pinning follows the protocol of Section~\ref{sec:protocol}. All experiments are conducted on this single machine and kernel. We discuss the scope and limitations of this platform in Section~\ref{sec:discussion}.

\subsection{Reference Database}\label{sec:refdb}

All experiments use a fixed reference database with a single table, \texttt{items(id INTEGER PRIMARY KEY, k1 INTEGER, k2 INTEGER, payload BLOB(100))}, and a secondary index on \texttt{(k1, k2)}. The database contains 600,000 rows, occupies 102.9 MiB (107{,}851{,}776 bytes), and uses 4 KB pages. The page composition, including the 92 interior pages and 26,239 leaf pages, is detailed in Section~\ref{sec:btree}. Three layout variants share the same logical content but differ in physical page arrangement: the default layout (\texttt{Default}) and the type-aware layout (\texttt{Clustered}) each contain 26,331 pages, and the \texttt{VACUUM} layout (\texttt{Vacuum}) contains 25,613 pages. A 10$\times$ scaled variant with 6,000,000 rows and 263,991 pages ($\sim$1 GiB) is used in the size-scaling experiments (Section~\ref{sec:evaluation}).

\subsection{Workloads}\label{sec:workloads}

We evaluate three measured read workloads that cover orthogonal dimensions of access-pattern variation. Scattered-Zipf-100K is read-only point queries from a scrambled Zipfian distribution over a 100K-key active domain. Uniform-100K is uniform read-only point queries over the same 100K-key active domain, used as a matched no-skew control. Tail-Mixed is a 20K-key interval crossing the database maximum, producing approximately 50\% successful and 50\% not-found queries. Alongside these we run one database-evolution schedule, Mixed-Mutation Churn, used only to age the database between measured probes and not latency-measured. We classify the workloads into three roles. Scattered-Zipf-100K, Uniform-100K, Tail-Mixed, and the Tail-Hit control are controlled read workloads. Latest-Aging and Short-Scan Aging are deterministic Python reconstructions of YCSB-D and YCSB-E semantics. Mixed-Mutation Churn is a mutation schedule, not a measured workload. We refer to every workload by its descriptive name throughout, which also avoids confusion with the standard YCSB core workloads A--F.

Scattered-Zipf-100K, Uniform-100K, and Tail-Mixed are designed to represent three distinct access characteristics: skew (Scattered-Zipf-100K), uniformity (Uniform-100K), and mixed tail-boundary lookups (Tail-Mixed). Scattered-Zipf-100K follows the access-distribution profile of YCSB-C~\cite{Cooper2010} (read-only Zipfian, $\alpha = 0.99$), with a key permutation that scatters hot keys across the 100{,}000-key active domain, analogous to YCSB's scrambled Zipfian. Our generator reproduces the distribution rather than YCSB's exact sampling implementation. Both Scattered-Zipf-100K and Uniform-100K follow the YCSB op-string format (\texttt{read <key>}, \texttt{update <key>}, \texttt{scan <key> <len>})\footnote{\url{https://github.com/ls4154/YCSB-cpp}}. Tail-Mixed and Mixed-Mutation Churn are custom designs specific to this study. They have no YCSB equivalent. Scattered-Zipf-100K and Uniform-100K draw keys from a 100,000-key active domain (ids 1 through 100,000), which lies entirely within the database's 600,000-key extent. Tail-Mixed instead draws uniformly over a 20,000-key interval (ids 590,000 through 609,999) that crosses the database maximum id of 600,000, so roughly half of its lookups fall beyond the maximum and become not-found probes. Each read workload executes 100,000 operations.

Three auxiliary robustness workloads support specific controls, all on the original layout (\texttt{Default}) only. Tail-Hit is a matched pure-hit control that draws the same-size tail range entirely within the existing key space (zero not-found), and it isolates the not-found effect in the attribution analysis of Section~\ref{sec:eval-attribution}. Latest-Aging (read-latest) and Short-Scan Aging (short-ranges) are deterministic Python reconstructions of the YCSB-D and YCSB-E core semantics rather than official YCSB traces, and they drive the static-plan staleness experiment of Section~\ref{sec:eval-robustness}: Latest-Aging's read hotspot moves over time (non-stationary), whereas Short-Scan Aging's is stationary. Neither Tail-Hit nor Latest-Aging/Short-Scan Aging alters the Scattered-Zipf-100K/Uniform-100K/Tail-Mixed first-query baselines. Hashed-Hotspot is a native YCSB hotspot read workload (hot-data-fraction $1\%$) whose hot keys are hashed across the physical key space, so the hot leaves are scattered rather than contiguous. It is used only in the cross-platform portability analysis of Section~\ref{sec:eval-portability} and is not equated with Tail-Mixed.

The three read workloads each produce the cold first-query baselines reported throughout this paper: under the default layout (\texttt{Default}), the median cold first-query latencies are 503~\textmu s for Scattered-Zipf-100K, 733~\textmu s for Uniform-100K, and 1072~\textmu s for Tail-Mixed. These baseline values are used as the denominator for all improvement calculations in Section~\ref{sec:evaluation}. The original workload traces are published with our artifact (checksummed). The accompanying generator reproduces their distributions and drives the 10-seed sensitivity analysis of Section~\ref{sec:stats}.

\subsection{OpenWhisk Portability Deployment}\label{sec:setup-openwhisk}

The cross-platform portability analysis (Section~\ref{sec:eval-portability})
runs the same prefetch toolchain inside a genuine container-based FaaS runtime,
Apache OpenWhisk, on a separate commodity x86 host with its own consumer-grade
NVMe SSD and a different Linux kernel. We compare only relative first-query
reductions across platforms and never absolute microseconds, so the deployment
exercises the serverless runtime together with its host rather than isolating the
container-runtime dimension from the underlying hardware. The action
loads an identical bound reference database, the original-layout (\texttt{Default})
\texttt{test.db} of 26{,}331 pages, and issues prefetch hints through the same
non-privileged application-layer interfaces (\texttt{mmap}, \texttt{madvise})
used on the workstation (Contribution~3). Nothing in the container requires
kernel, FTL, or runtime modification.

Each measured invocation is one arm of an A/B pair: a same-condition baseline
arm and a strategy arm, scheduled under a block-union paired design with
position balancing. We report the \emph{fresh-handle} paired first-query, a per-invocation
handle-mode measurement, distinct from the external-warmer deployment boundary
of the cost model (Section~\ref{sec:methodology}), which is a
deployment-feasibility and relative-effectiveness signal rather than an absolute
strategy-performance estimate. Absolute microseconds are never compared between
OpenWhisk and the workstation. The comparison quantity is the relative
first-query reduction $R$ defined in Section~\ref{sec:eval-portability}.

Seven frozen campaigns comprise 5{,}756 invocations and 2{,}878 A/B pairs. The
campaign totals are bookkeeping only, and effect estimates are never pooled
across campaigns. Together the campaigns give complete coverage of the
strategy$\times$workload cells the workstation ran, 65 of 65: 55 first-query
effectiveness cells plus 10 delivery-order \texttt{LP} cells.

\section{Evaluation}\label{sec:evaluation}

Our evaluation answers three questions. \textbf{RQ1:} does a lower first-query latency imply a faster cold start? Sections~\ref{sec:eval-fq} and~\ref{sec:eval-tradeoff} show that it does not: once delivery cost is charged, the first-query ranking can reverse. \textbf{RQ2:} given critical-path cost accounting, what should we prefetch? Section~\ref{sec:eval-attribution} shows the answer is a small coverage set: interior-navigation coverage is a robust, interpretable default, hot leaves help only under an independently verified hotspot, and at matched footprint a sophisticated selector shows no demonstrated advantage over a frequency-ranked dump. \textbf{RQ3:} are the end-to-end design conclusions robust to workload and system variation, and does the underlying first-query effectiveness survive deployment in a FaaS runtime? Section~\ref{sec:eval-robustness} tests the end-to-end conclusion under workload and system variation on the controlled workstation, across six robustness axes. Section~\ref{sec:eval-portability} asks the narrower deployment question of whether the first-query effectiveness signal survives on Apache OpenWhisk, where all 41 strong-workstation first-query cells remain effective and first-query effectiveness ranks correlate at Spearman $\rho\approx0.76$ to $0.81$.

\subsection{First-Query Gains and Workload-Dependent Ceilings}\label{sec:eval-fq}

We begin by establishing the first-query latency improvements achieved by each strategy, before accounting for prefetch preprocessing in Section~\ref{sec:eval-tradeoff}. Under a cold OS page cache, the baseline first-query latencies are 503 \textmu s for Scattered-Zipf-100K, 733 \textmu s for Uniform-100K, and 1072 \textmu s for Tail-Mixed (Section~\ref{sec:workloads}). The cache-dump strategy \texttt{Dump} achieves the lowest first-query latency across all three workloads: 98 \textmu s for Scattered-Zipf-100K ($-80\%$), 100 \textmu s for Uniform-100K ($-86\%$), and 96 \textmu s for Tail-Mixed ($-91\%$). If the evaluation stopped at first-query latency, \texttt{Dump} would be the unambiguous winner. The targeted strategies achieve reductions ranging from $-27\%$ to $-83\%$, with the specific ceiling depending on the workload.

Table~\ref{tab:ceiling} summarizes the workload-dependent benefit ceiling for first-query improvement. Scattered-Zipf-100K, which exhibits a skewed Zipfian access pattern, concentrates first-query probability on a small set of leaves (all pages are nonetheless cold at measurement time). Prefetching interior pages alone captures the dominant benefit, yielding $-27\%$ to $-29\%$ improvement. Adding more hot leaves through \texttt{Skel+500} reaches $-64\%$, and the full cache dump reaches $-80\%$, but the marginal gain of adding leaves beyond the interior skeleton is modest. Uniform-100K, which accesses keys uniformly at random, has no natural hot set. Every query touches a cold leaf, and interior-only prefetching is capped at approximately $-44\%$. Only the full cache dump, which loads the entire resident working set, reduces first-query latency further to $-86\%$. Tail-Mixed, which reads a high-key tail range roughly half of which lies beyond the database's maximum key, faces cold leaves on every query. The access-pattern strategy \texttt{Skel+10} breaks through the interior-only ceiling of $-38\%$ largely because the $\sim$50\% not-found probes concentrate on the rightmost leaf, which \texttt{Skel+10} prefetches, achieving $-83\%$ first-query reduction (a key-range artifact, not general tail prediction, Section~\ref{sec:eval-attribution}).

The effectiveness of structural prefetching, \texttt{Skel-N}, depends on both the workload and the physical layout. On Scattered-Zipf-100K, prefetching the first five interior pages reaches a plateau at approximately $-27\%$ to $-29\%$ first-query reduction, and additional interior pages beyond $N=5$ provide no further benefit. Uniform-100K exhibits the same pattern: $N=5$ is already sufficient, and the plateau sits at approximately $-44\%$. Tail-Mixed, in contrast, requires nearly all 92 interior pages ($N \approx 92$): \texttt{Skel-N} selects interiors by file offset, while the interiors covering Tail-Mixed's high-key tail range sit mid-file, so offset-order selection misses them until $N$ spans nearly the full set. Prefetching only a single interior page ($N=1$) is counter-productive on Scattered-Zipf-100K: the \texttt{madvise} dispatch overhead exceeds the coverage benefit, making first-query latency approximately $+31\%$ worse than the same-batch baseline. On Uniform-100K and Tail-Mixed, $N=1$ is slightly better than the baseline by a few percent. The mechanism behind the \texttt{Skel-N} plateau is subtle. At first-query time, both interior and leaf pages are equally cold. Prefetching interior pages removes interior faults but leaves the first leaf fault intact. After the query stream warms up, the hot leaves corresponding to frequently accessed keys become naturally resident in the cache. The interior pages, however, remain the only shared bottleneck across all queries. Prefetching the interior skeleton is therefore sufficient for workloads with stable hot keys, while workloads whose first queries strike cold leaves require more: Uniform-100K, with no natural hot set, is served only by the full dump, whereas Tail-Mixed's concentrated tail region makes access-frequency targeting effective. The effect of the hot key location, such as low-id hotspots, is secondary. The shape of the N-sweep is consistent across hotspot variants in our artifact.

\subsection{The Preprocessing Trade-off}\label{sec:eval-tradeoff}

The first-query results in Section~\ref{sec:eval-fq} establish a clear winner: \texttt{Dump} minimizes first-query latency across all three workloads, achieving reductions of $-80\%$ to $-91\%$. If the evaluation stopped at first-query latency, the conclusion would be unambiguous. However, first-query latency excludes the preprocessing cost of issuing prefetch hints. The end-to-end cold-start latency that a user experiences includes both the first query and the prefetch itself. Table~\ref{tab:overhead} decomposes this preprocessing cost for each strategy.

\subsection{Attribution: Ablation and Competitive Baselines}\label{sec:eval-attribution}

The large single-instantiation result of Section~\ref{sec:eval-tradeoff} on Tail-Mixed combines two selection levers: page-type awareness (interior pages) and access-frequency awareness (hot leaves). We isolate their individual contributions using an exact decomposition of the \texttt{Skel+10} hotset. This attribution required correcting a subtle estimator artifact. Our original hot-leaf ranking broke frequency ties by first-seen order. On a tied-count workload this preferentially selected the earliest-observed leaves, which coincide with the measured first query and leak into the hotset. We replaced it with a deterministic, trace-order-independent tie-break (frequency descending, then page number ascending) and re-measured the affected cells in a same-batch rerun. The corrected numbers below reverse the pre-fix attribution:

\begin{itemize}
    \item \texttt{Skel}: page-type lever only, prefetching resident interiors after workload warmup.
    \item \texttt{leaf\_freq\_K10}: access-frequency lever only, prefetching the top-10 most frequently accessed leaves.
    \item \texttt{leaf\_rand\_K10}: control group, prefetching 10 leaves of the same type (leaf\_table) drawn uniformly at random, controlling for page count and type while isolating the effect of frequency ranking.
    \item \texttt{Skel+10}: union of \texttt{Skel} and \texttt{leaf\_freq\_K10}, the exact decomposition.
\end{itemize}

The control group is the crucial design element: \texttt{leaf\_rand\_K10} and \texttt{leaf\_freq\_K10} have the same page count (10) and the same page type (leaf), differing only in whether selection is frequency-based or random. Any difference between them is attributable purely to access-frequency awareness.

The corrected ablation and competitive-baseline experiments run as a single same-batch 10-seed rerun with paired baselines. Cross-seed means therefore differ from the single-instantiation numbers of Sections~\ref{sec:eval-fq} and~\ref{sec:eval-tradeoff}. Table~\ref{tab:ablation} presents the cross-seed means for Tail-Mixed. The interior-only lever, \texttt{Skel}, is $-43\%$ first-query and $-36\%$ end-to-end, and is the only \emph{robust} contributor (CI excludes zero). The random-leaf control is net-harmful in end-to-end ($+7\%$), showing that loading extra leaves without a real hotspot costs deliver time for no coverage. Crucially, the frequency-selected leaves alone, \texttt{leaf\_freq\_K10}, are only $-3\%$ end-to-end with a confidence interval that crosses zero, i.e.\ a tie: their pre-fix value of $-40\%$ was almost entirely first-op leakage. The combined strategy, \texttt{Skel+10}, reaches $-63\%$ first-query and $-55\%$ end-to-end, but is bimodal across first-op hit/miss seeds (discussed below). The attribution therefore reverses relative to the pre-fix analysis: page-type (interior) awareness is the robust lever and the enabler of any leaf benefit (a leaf is useless while its interior path is uncached), whereas leaf-frequency alone is not a robust standalone signal on this workload.

Changing the physical layout from the default (\texttt{Default}) to the type-aware layout (\texttt{Clustered}) does not change the selection story: it increases the number of interior pages prefetched by \texttt{Skel} on Tail-Mixed from 4 to 48, but the warm e2e improvement is slightly worse ($-63\%$ vs $-75\%$ for \texttt{Default}; both from the layout-pair batch, which is the only one that measured \texttt{Clustered}), consistent with the layout negative result we detail below.

The corrected ablation establishes an asymmetric hierarchy, not two equal levers. Page-type awareness is the robust default: it carries Uniform-100K, supplies the interior skeleton for Scattered-Zipf-100K and Tail-Mixed, and is the prerequisite for any leaf benefit. Access-frequency leaf selection is a conditional add-on: it contributes a genuine, robust bonus only where a real hotspot exists (the Zipfian skew of Scattered-Zipf-100K), and is a tie on the uniform-hit portion of Tail-Mixed. What looked, before the tie-break fix, like a large access-frequency contribution on Tail-Mixed was largely first-op leakage. The residual leaf signal on Tail-Mixed stems from its not-found rightmost-leaf concentration, discussed next, not from general leaf predictability.

The reason Tail-Mixed produces a large but narrow result is a property of its key range rather than of tail reads in general. Tail-Mixed draws uniformly over a high-key range whose upper half exceeds the reference database's maximum key, so approximately half of its lookups are not-found probes. Every such probe descends the B+tree right edge to the same rightmost leaf, which therefore becomes an extreme, key-range-induced hotspot. Consequently Tail-Mixed's corrected \texttt{Skel+10} result is bimodal across seeds: when the measured first query is itself a not-found probe it hits this hotspot ($\approx -70\%$), and when it is a genuine hit it falls back to the interior-skeleton regime ($\approx -31\%$), for a cross-seed mean of $-55\%$. To confirm that this is a not-found artifact rather than a general uniform-tail-read benefit, we run a matched pure-hit control on the original layout, Tail-Hit, which draws the same-size tail range entirely within the existing key space (zero not-found). On this control the corrected \texttt{Skel+10} returns to $\approx -27\%$, statistically matching interior-only \texttt{Skel} ($-28.5\%$) and a footprint-matched frequency dump ($-30.6\%$): once the not-found concentration is removed, leaf-frequency selection adds essentially nothing beyond the interior skeleton. We report the large Tail-Mixed number therefore as a scoped, mechanism-specific result, not as the paper's general finding.

We next ask whether the cache-dump strategies used in Section~\ref{sec:eval-tradeoff}, specifically \texttt{Dump}, are an unfairly weak baseline. To address this concern, we design two competitive baselines that port the page-selection core of representative prior systems onto our common substrate, SQLite over the OS page cache, so that they can be evaluated on the cold-start critical path under the same cost accounting. \texttt{Dump} ports the full-working-set dump-and-reload core of InnoDB's buffer pool dump/load: it captures the entire resident working set (approximately 4,400 pages, 17.7 MB on Scattered-Zipf-100K/Uniform-100K, 1.8 MB on Tail-Mixed) and reloads it at cold start. \texttt{Dump-N} implements a frequency-ranked dump in the spirit of Pre-Buffer's hot-page selection~\cite{Yi2026}: our variant replays each query's root-to-leaf traversal, counts page visits, and dumps the top-$N$ ranked pages ($N \in \{14, 28, 100, 500\}$). InnoDB's partial dump ranks by LRU recency, whereas Pre-Buffer ranks by access frequency, and our arm implements the frequency variant. We deliberately reproduce only the selection mechanism, not the surrounding orchestration (InnoDB's startup-time reload and Pre-Buffer's background prefetch thread, Jaccard-similarity workload-change detection, dedicated prefetch buffer, and page-cache-bypassing Direct I/O), because that orchestration runs off the critical path and is orthogonal to our question. Neither prior system accounts for prefetch delivery cost on the user-facing critical path. By porting their selection cores into our cost-accounted first-query harness, we show that frequency-ranked selection at matched footprint ties our targeted strategy on both broad and narrow workloads, while the full-working-set dump, the InnoDB core, regresses warm-process end-to-end latency by up to $+762\%$ (cross-seed mean, as we show below). We sweep $N \in \{14, 28, 100, 500, \text{full}\}$.

Table~\ref{tab:competitive} shows the e2e warm results for a representative subset: the targeted strategy \texttt{Skel+10}, the tuned dump at its sweet spot (\texttt{Dump-14}), a larger tuned dump (\texttt{Dump-500}), and the full dump (\texttt{Dump}). The competitive sweep supports three conclusions. First, end-to-end performance monotonically worsens with dump footprint: full dump regresses by $+762\%$ (cross-seed mean) on Scattered-Zipf-100K, compared to the single-instantiation figure of $+1319\%$ in Table~\ref{tab:e2e-ac}, and by $+730\%$ on Uniform-100K, demonstrating that the deliver cost of large hotsets is the fundamental problem, not the dump mechanism itself. Only small, frequency-ranked partial dumps win, with sweet spots at $N \approx 14$ to 28. Second, on the broad workloads Scattered-Zipf-100K and Uniform-100K, \texttt{Dump-N} with matched footprint effectively matches \texttt{Skel+10}: Scattered-Zipf-100K $-37\%$ (\texttt{Dump-28}) vs $-38\%$ (\texttt{Skel+10}), Uniform-100K $-27\%$ (\texttt{Dump-14}) vs $-24\%$ (\texttt{Skel+10}), and CIs overlap. Page-type knowledge is not necessary for these workloads, and frequency ranking alone suffices. Third, on the narrow workload Tail-Mixed, the corrected same-batch comparison shows \emph{no} advantage for explicit type awareness: \texttt{Skel+10} achieves $-55\%$ (CI $[-67, -42]$) and matched \texttt{Dump-14} achieves $-55\%$ (CI $[-67, -43]$), with essentially fully overlapping CIs, so the two are statistically indistinguishable. The pre-fix appearance of a robust $-72\%$ vs $-57\%$ gap was an artifact of the first-op tie-break leakage. This is consistent with the ablation: because Tail-Mixed's leaf signal comes from a not-found rightmost-leaf concentration that a frequency-ranked dump also captures, footprint-matched frequency ranking recovers a similar page set. Explicit page typing is an interpretable way to \emph{guarantee} interior-skeleton coverage, but it does not uniquely win on Tail-Mixed.

Two prior-art arms cited in Section~\ref{sec:related} remain, each isolating a dimension the competitive baselines above hold fixed.

\textbf{Delivery order (libprefetch).} The competitive baselines above vary the prefetch \emph{set} at a fixed delivery order. The core contribution of libprefetch~\cite{VanDeBogart2009} is the opposite, varying delivery \emph{order} (C-LOOK offset sorting) at a fixed set. We reproduce it as an ordering-only comparison: two arms deliver the identical $\sim$18\,MB working set (whose sorted-order page set is identical to \texttt{Dump}), one in ascending file-offset order (\texttt{LP-sorted}), one shuffled (\texttt{LP-shuf}). On NVMe the ordering penalty survives only in the deliver term: synchronous \texttt{pread} delivery is $10$ to $16\times$ slower shuffled than sorted ($15.6\times$ Scattered-Zipf-100K, $15.1\times$ Uniform-100K, $10.5\times$ Tail-Mixed), hundreds of milliseconds of avoidable serialized transfer. First-query latency is essentially unchanged between the two orderings (a warm control: both arms deliver the same pages). The entire ordering effect falls in the deliver term, orders of magnitude larger than any first-query difference. The penalty is specific to synchronous \texttt{pread}, which serializes the transfer. Asynchronous \texttt{fadvise} dispatch, which only hands the kernel a hint, shows no ordering effect (deliver ratio $\approx 1.0$ on all three workloads). Without a block-level trace we make no device-mechanism claim beyond this synchronous/asynchronous split. libprefetch is thus orthogonal to our set-selection contribution: a delivery-scheduling optimization whose only NVMe residue is a deliver-term cost that leaves first-query latency untouched.

\textbf{Learned page-transition prefetching (Chen lineage).} The second arm is a learned prefetcher in the lineage of Chen et al.~\cite{Chen2021}: a first-order Markov page-transition model that computes finite-horizon expected page visits from the B$^+$tree root and prefetches the top-$N$. We evaluate it under leave-one-seed-out (LOSO) cross-validation across the 10 workload seeds (train on nine, test on the held-out seed) so no test trace informs its own prefetch set. At matched footprint it reduces cold first-query latency by $-39.6\%$ (Scattered-Zipf-100K), $-36.6\%$ (Uniform-100K), and $-65.4\%$ (Tail-Mixed), a $-37\%$ to $-69\%$ range across cells with every 95\% CI excluding zero, at $100\%$ delivery on verified-cold caches. It ties footprint-matched frequency ranking and targeted prefetch on Uniform-100K and Tail-Mixed (overlapping CIs). On Scattered-Zipf-100K, the learned model reaches about $-40\%$, compared with roughly $-51\%$ for the same-budget frequency-ranked and hot-leaf arms, whose confidence intervals overlap, so we do not claim a statistically resolved ranking. The learned transition model provides no demonstrated advantage over the simpler frequency-ranked baseline. (An earlier single-fold analysis reported a more optimistic held-out figure, but the honest LOSO mean supersedes it.) These two arms therefore reinforce the central finding: neither delivery-order scheduling nor a learned transition model outperforms a small, soundly-selected prefetch set.

We now return to the physical layout rewriter (\texttt{Clustered}) introduced in Section~\ref{sec:layout}. Our evaluation finds no scenario in which \texttt{Clustered} outperforms the default layout (\texttt{Default}) when combined with access-pattern prefetching. The best warm e2e on each workload is achieved with \texttt{Default} plus access-pattern targeting: Scattered-Zipf-100K 452 \textmu s vs \texttt{Clustered} 523 \textmu s, Uniform-100K 509 \textmu s vs \texttt{Clustered} 701 \textmu s, and (from the tie-break-corrected batch) Tail-Mixed \texttt{Skel+10} 265 \textmu s vs \texttt{Clustered} 317 \textmu s. Each orig-vs-\texttt{Clustered} pair is same-batch. The Tail-Mixed pair uses the corrected \texttt{tiebreak\_fix} values (orig $-75\%$, \texttt{Clustered} $-63\%$). The type-aware layout produces slightly larger percentage improvements for structural prefetching (on Scattered-Zipf-100K, \texttt{Skel-92} first-query goes from $-30\%$ to $-32\%$), but this is an artifact: the pread first-query floor under \texttt{Clustered} is 187 \textmu s versus 187 \textmu s under \texttt{Default}. The larger percentage stems entirely from a raised baseline (523 to 658 \textmu s, $+26\%$), not from a lower absolute latency. Clustering interiors at the file head pushes leaves to higher offsets, raising the cold-leaf-fault baseline. The absolute benefit of interior prefetching does not improve. A production system arrives at the same conclusion from the
opposite direction: the \texttt{.dbi} side file (Section~\ref{sec:layout}) avoids in-place reordering entirely, sidestepping precisely the displacement penalty we quantify here. The narrow conditions under which \texttt{Clustered} could be net-positive, (i) prefetching is definitely deployed, (ii) only structural prefetching is available (no access-pattern observation), and (iii) the workload is sufficiently skewed, are not simultaneously met in any of our Scattered-Zipf-100K/Uniform-100K/Tail-Mixed cells. We therefore recommend the default layout (\texttt{Default}) for production use, and treat \texttt{Clustered} as a negative result under our evaluated workloads.

\subsection{Robustness}\label{sec:eval-robustness}

We validate the headline conclusions across six robustness axes. All results in this section use the cross-seed classifications defined in Section~\ref{sec:stats}: \textit{robust} (95\% CI excludes zero), \textit{directional} (CI crosses zero but at least 7 of 10 seeds agree in sign), and \textit{tie} (effects within the noise). Each robustness axis is evaluated on a separate batch (distinct machine-state groups). Comparisons are within-axis only. Absolute latencies may differ across axes, but the relative effects and verdicts are internally consistent.

\textbf{Workload instantiation sensitivity.} The single-workload numbers reported in Sections~\ref{sec:eval-fq} and~\ref{sec:eval-tradeoff} are point estimates from one instantiation of each workload. To quantify whether these conclusions generalize across different random samples of the same distribution, we generate 10 independent random seeds for each of Scattered-Zipf-100K, Uniform-100K, and Tail-Mixed and run the full measurement matrix on each seed. Table~\ref{tab:seeds} reports the cross-seed warm-process e2e improvement for each strategy on its representative workload.

The sweep yields three findings. First, the robust, general result is the interior skeleton: \texttt{Skel} improves warm-process e2e by roughly $-25\%$ to $-30\%$ across Scattered-Zipf-100K, Uniform-100K, and the pure-hit control (Scattered-Zipf-100K $-25\%$, Uniform-100K $-25\%$, Tail-Hit $-28.5\%$), all with CIs excluding zero. The larger $-36\%$ belongs to Scattered-Zipf-100K's \texttt{Skel+10} genuine-skew bonus and to Tail-Mixed's not-found-inflated \texttt{Skel}, not to the general skeleton. Second, Tail-Mixed \texttt{Skel+10}'s cross-seed mean is $-55\%$ $[-67, -43]$ but bimodal (Section~\ref{sec:eval-attribution}). Its magnitude is not stable and reflects Tail-Mixed's not-found concentration rather than a general access-pattern win. The three workloads' best access-pattern strategies are all cross-seed improvements (Scattered-Zipf-100K \texttt{Skel+10} $-36\%$ $[-50, -23]$, Uniform-100K \texttt{Skel} $-25\%$ $[-32, -16]$), but the robust, portable claim is the interior skeleton, not the Tail-Mixed headline number. Third, the structural heuristic \texttt{Skel-5} does not survive: on Scattered-Zipf-100K it is \textit{tie} ($-5\%$, CI crosses zero, 6/10), and on Uniform-100K the verdict is \textit{directional}, toward regression: 8 of 10 seeds worsen (median $+5\%$), with the cross-seed mean pulled to $-1\%$ by two strongly improving seeds. The structural heuristic is not merely unstable but, in most instantiations, actively harmful. The robustness of the headline is carried entirely by access-pattern strategies. Structural prefetching without access observation is unreliable.

The methodological lesson from the 10-seed sweep is that single-workload point estimates can be misleading. The main batch happened to draw a Scattered-Zipf-100K instance whose first query was unusually cheap (baseline $\sim$520 \textmu s versus a cross-seed typical $\sim$900 \textmu s), leading to a cross-seed corrected improvement of $-36\%$ compared to the single-instantiation estimate of $-11\%$. Conversely, the same batch overestimated Uniform-100K \texttt{Skel-5} at $-34\%$, which is near zero in the cross-seed mean ($-1\%$). Both biases are only detectable with multi-seed sampling, validating the methodology of Section~\ref{sec:stats}.

\textbf{Memory pressure.} Serverless platforms enforce per-function memory caps via cgroup \texttt{MemoryMax}. When the cap falls below the working set, page reclaim competes with prefetch delivery. We sweep caps from 16 MB to 6 MB, representing 0.92$\times$ to 0.35$\times$ the working set for Scattered-Zipf-100K and Uniform-100K. Figure~\ref{fig:ram} shows the result. The five targeted strategies (hotsets ranging from 20 KB to 2 MB) maintain 100\% delivery across all caps. Their hotsets are orders of magnitude smaller than the memory cap, so reclaim never touches them. First-query latency remains flat. In contrast, \texttt{Dump}, whose hotset is the full working set (17.7 MB), loses delivery linearly as the cap shrinks (100\% to 20\%), and its first-query latency jumps directly from 98 \textmu s to the cold baseline of approximately 500 \textmu s as soon as delivery drops below 100\%. The cache-dump approach exhibits no graceful degradation. It is all-or-nothing. For Tail-Mixed, whose working set is only $\sim$1.8 MB, the cap cannot be meaningfully reduced below the working set without hitting the measurement floor. Its RAM robustness is a deductive consequence of its hotset being smaller than any measurable cap and is not empirically tested in this axis.

\textbf{Write churn.} Serverless data stores ingest continuously between invocations. We therefore subject the database to 50,000 mutations (10 rounds of 5,000 writes) and measure the static $t=0$ hotset across 11 checkpoints. This churn batch predates the trace-order-independent tie-break correction. We therefore use it only to assess within-batch flatness across checkpoints, and treat the absolute level as diagnostic rather than as a corrected estimate of the \texttt{Skel+10} effect magnitude. Within the same pre-fix estimator and batch, the frozen plan does not show a systematic latency increase across checkpoints when the read hotspot remains stationary: on Tail-Mixed, \texttt{Skel+10} maintains $\sim$82--89 \textmu s across checkpoints (aside from one transient spike at checkpoint 4), compared to a baseline of $\sim$580 \textmu s (these absolute microseconds are pre-fix diagnostic values, not a corrected magnitude). Uniform-100K, which has no natural hot leaves, is similarly flat. Under this stationary-read-hotspot configuration, no plan refresh was needed to preserve the within-batch trend over 50k mutations. This scope is important: write churn perturbs page layout but leaves the \emph{read} hotspot in place. A read hotspot that moves over time is a distinct axis, the non-stationary Latest-Aging versus stationary Short-Scan Aging contrast examined next, under which a frozen frequency plan does decay. The corresponding figure is available in our artifact.

\textbf{Static-plan staleness under a moving hotspot.} We ask what happens when the read hotspot itself drifts, using two aging robustness workloads that are deterministic Python reconstructions of YCSB semantics (Section~\ref{sec:workloads}): Latest-Aging (read-latest), whose hotspot moves as new keys are inserted (non-stationary), and Short-Scan Aging (short-ranges), whose hotspot is stationary. A frozen $t{=}0$ plan is replayed across 11 checkpoints (10 seeds, bootstrap 95\% CI). Under Latest-Aging, the frozen \emph{frequency} plan (\texttt{Skel+10-static}) decays as the hotspot moves away from it: its warm first-query benefit erodes from $-50\%$ at checkpoint~0 to $-33\%$ at checkpoint~10, while the \emph{structural} plan (\texttt{Skel-92-static}), which covers the navigation skeleton independent of which keys are hot, holds at $-53\%$ across all checkpoints. Under the stationary Short-Scan Aging, both plans stay flat ($-53\%\!\to\!-55\%$ frequency, $-53\%\!\to\!-51\%$ structural). A static frequency plan is therefore safe only while the read hotspot is stationary. Once it moves, structural coverage is the durable choice, matching the recommendation in Table~\ref{tab:guidance}. The corresponding figure is available in our artifact.

\textbf{Cadence and MAP\_SHARED.} The threat is a prefetched hotset cooling between invocations. With \texttt{mmap(MAP\_SHARED)} a single background warmer re-warms the hotset for all processes sharing the OS page cache, at a configurable cadence. At cadence values of 1 s and 5 s, first-query latency is maintained at 26 \textmu s and 29 \textmu s, respectively. At 30 s or never, it regresses to 281--305 \textmu s, near the no-prefetch baseline. There is no single best cadence: lower cadence holds warmth at the cost of extra I/O and CPU, and the operator selects a point on this frontier from the workload's query interval.

\textbf{Database size scaling.} We scale the reference database by $10\times$ to $\sim$1 GiB (6 million rows, 263,991 pages) and rerun the experiment on a separate batch. The first-query improvement is size-robust: across the 18 (workload $\times$ strategy) cells, all cells show the same direction of improvement as on $\sim$103 MiB, and all 1 GiB cells are robust (CI excludes zero). The warm-process e2e sensitivity is concentrated on Tail-Mixed for dump-style strategies: \texttt{Dump} goes from $-9\%$ on $\sim$103 MiB to $+139\%$ on 1 GiB, and \texttt{Skel+500} goes from $-31\%$ to $+35\%$, as the resident working set for Tail-Mixed expands from 483 to 984 pages, doubling the deliver cost. In contrast, the tie-break-unaffected interior skeleton \texttt{Skel} remains a robust win on Tail-Mixed at both sizes, and the size story is carried by the deliver-cost trend rather than by any corrected leaf-selector magnitude: the cache-dump deliver trap worsens with database size while frugal skeleton prefetch stays effective. (The pre-fix \texttt{Skel+10} figures of $-70\%$/$-68\%$ at $\sim$103~MiB/1~GiB are diagnostic only. The corrected leaf-selector magnitude was not re-validated across sizes.) The corresponding figure is available in our artifact.

\subsection{Cross-Platform First-Query Effectiveness Portability}\label{sec:eval-portability}

The results so far were measured on a single workstation harness. This
experiment does not re-evaluate the end-to-end cost ordering on OpenWhisk. It
asks the narrower deployment question of whether the first-query effectiveness of
the prefetched page sets survives the FaaS runtime and host environment. We
replicated the strategy matrix on an Apache OpenWhisk deployment
(Section~\ref{sec:setup-openwhisk}) and compared it to the workstation cell by
cell, using the frozen non-pooled evidence defined in
Section~\ref{sec:setup-openwhisk}.
First-query effectiveness is the relative first-query reduction against the
same-condition baseline, $R = (\mathit{fq}_{\text{base}} -
\mathit{fq}_{\text{strat}}) / \mathit{fq}_{\text{base}}$. Only this relative
quantity is comparable across platforms, and we never compare absolute
microseconds between the two. As noted in Section~\ref{sec:setup-openwhisk}, this
fresh-handle paired first-query (a per-invocation handle mode, not the
external-warmer deployment boundary) is a deployment-feasibility and first-query
effectiveness signal, not an absolute strategy-performance estimate. This
validation runs on a separate commodity x86 host with its own consumer NVMe and a
different kernel. It exercises the FaaS runtime together with its host and does
not isolate the container-runtime dimension or establish hardware portability.
Over the strategy$\times$workload cells both platforms ran, coverage is complete:
all 65 of 65 cells, comprising 55 first-query effectiveness cells plus 10
delivery-order \texttt{LP} cells.

We classify each cell's effectiveness as effective ($R \geq 0.10$), harmful
($R \leq -0.10$), or neutral, and call a workstation cell strongly effective
when $R_{\text{ws}} \geq 0.30$. We report the per-cell rank correlation over
three nested subsets: all 55 first-query cells, a high-confidence subset of 46
(dropping low-sample cells), and a high-confidence \emph{clean} subset of 42
(also dropping the 4 position-sensitive cells whose baseline-first and
target-first subsets disagree in sign). Seven of the 55 first-query cells were re-measured with position-balanced
replications after their initial measurements showed low sample counts or
pair-position imbalance. The campaigns and the per-cell precedence rule were
specified before the replication runs. Every OpenWhisk statistic reported in this
paper uses the revised measurements for those seven cells and the original
measurements for the remaining 48. The historical values are retained in the
artifact for provenance.

Three principles summarize the takeaways. First, the cache-dump strategy (\texttt{Dump}) minimizes first-query latency but is unsuitable for the cold-start critical path in all but the smallest working-set scenarios. Its deliver overhead dominates response time, and its value lies in steady-state average latency rather than in user-facing first-query response. Moreover, even the small-working-set exception on Tail-Mixed erodes as the database grows (Section~\ref{sec:eval-robustness}), further reinforcing that cache-dump is not a robust critical-path solution. Second, the interior skeleton on the original layout (\texttt{Default} + \texttt{Skel}) is the recommended default for warm-process serverless deployments: it delivers consistent end-to-end improvements across all three workload types, survives cross-seed validation as robust, and has a memory footprint under 2 MB. Third, the structural heuristic (\texttt{Skel-5}) should not be used alone. Its single-workload wins on Scattered-Zipf-100K and Uniform-100K do not survive cross-seed validation. In most workload instantiations it is neutral or harmful. If structural prefetching is the only available mechanism, it should be paired with access-pattern observation or replaced by prefetching the full interior set ($N=92$, 368 KB), which does not depend on offset-order selection.

\section{Discussion and Limitations}\label{sec:discussion}

All experiments run on a single commodity x86 machine with a consumer-grade Gen4 NVMe SSD and a single Linux kernel version. Absolute microsecond latencies depend on the hardware, kernel, and runtime. The cost-accounting methodology is intended to transfer to platforms sharing the same warm-process, cold-data model. Whether the first-query effectiveness of the prefetched page sets carries over to a genuine FaaS runtime is an empirical question we test directly with an Apache OpenWhisk deployment (Section~\ref{sec:eval-portability}). On OpenWhisk, all 41 workstation cells with strong first-query effectiveness (relative first-query reduction $R_{\text{ws}}\ge0.30$) remain effective. Across the 55 matched first-query cells, continuous first-query effectiveness ranks show substantial but imperfect agreement (Spearman $\rho\approx0.76$ to $0.81$), with 46 of 55 categorical direction agreement. This validates deployability and first-query effectiveness portability, not cross-platform end-to-end ranking, using the frozen non-pooled evidence defined in Section~\ref{sec:setup-openwhisk}. The OpenWhisk fresh-handle paired first-query (a per-invocation handle mode, not the external-warmer deployment boundary of the cost model) is a deployment-feasibility and first-query effectiveness signal, not an absolute strategy-performance estimate. In particular, our measurements characterize the local-storage tier that production object-storage architectures interpose as a cache layer (e.g., Cloudflare D1's local-disk caching over R2~\cite{CloudflareD1}). The purely remote tier replaces the OS page cache with VFS-level range requests, changing the mechanism while preserving the dependent-fault-chain structure and multiplying per-fault cost by three to four orders of magnitude. This FaaS-runtime validation runs on a separate commodity x86 host with its own consumer NVMe and a different Linux kernel, so it exercises the container-based runtime together with its host rather than isolating the runtime dimension or establishing hardware portability. The few per-cell disagreements are confined to strategies neutral on at least one platform and to position-sensitive cells (Section~\ref{sec:eval-portability}). None is a regression of a workstation-effective strategy. Systematic portability across diverse hardware classes and to commercial FaaS providers remains future work.

Our stable \texttt{Dump} fast-path anchor exhibits approximately 10\% to 15\% session-to-session absolute drift. Individual latency cells can shift more substantially across machine-state groups. Diagnostics associate this drift with SSD internal state and CPU thermal conditions. The \texttt{Dump} anchor's first-query latency is independent of the workload key distribution, so we use it to monitor drift and anchor every effect estimate to a same-batch baseline. We never compare absolute latency across independent batches.

The workload coverage spans three distribution families, skew (Scattered-Zipf-100K), uniformity (Uniform-100K), and mixed tail-boundary lookups (Tail-Mixed), with 10-seed sampling to cover within-family variation. It does not cover real-world mixed read-write traces or distribution families beyond these three. The RAM robustness of Tail-Mixed remains deductive rather than empirically measured, because its working set (approximately 1.8 MB) falls below the measurable cgroup pressure floor. Constructing a larger working-set variant of Tail-Mixed is future work.

The measurement methodology stops at the OS page cache layer and cannot control SSD-internal FTL behavior, garbage collection, or wear leveling. The long-term evolution of page layout under sustained churn, beyond the 50k-mutation window, remains unobserved. A FEMU-based study is a natural extension.

The warm-process model differs from a full cold reboot by approximately 1 to 3 \textmu s of CPU cache warm-up bias, less than 1\% of the cold baseline. The strict cold-start mode, which quantifies this bias precisely, is left as future work.

\section{Conclusion}\label{sec:conclusion}

Serverless functions backed by SQLite experience a persistent cold-start bottleneck when the OS page cache is empty after idle periods, making the first query orders of magnitude slower than subsequent ones. Our central argument is methodological: evaluating cold-start prefetch by post-prefetch first-query latency alone is insufficient, because the prefetch preprocessing itself lies on the user-visible critical path. Once that preprocessing is charged (decomposed into open and deliver terms under a warm-process/integrated and an external-warmer deployment boundary), the strategy ranking changes: the cache-dump strategy that minimizes first-query latency, \texttt{Dump}, regresses end-to-end cold starts by roughly an order of magnitude on broad workloads due to deliver overhead of 0.8 to 7 ms. The design point that survives this accounting is frugal coverage. A small-footprint set covering the interior navigation path (\texttt{Skel}, footprint under 2 MB) achieves roughly $25$ to $30\%$ warm-process end-to-end improvement across the evaluated pure-hit workloads, robust across seeds. Hot leaves help only under an independently verified concentrated hotspot (raising Scattered-Zipf-100K from about $-25\%$ to $-36\%$ under genuine Zipfian skew). Crucially, at matched footprint a frequency-ranked dump is statistically indistinguishable from the type-aware selector, so what carries the result is footprint and sound coverage rather than selector sophistication. Structural page-type knowledge remains valuable as an interpretable coverage guarantee and because structural coverage stays stable when the read hotspot moves, whereas a frozen frequency plan decays. A mixed tail-boundary workload whose range is roughly half not-found high-key probes yields a larger but narrowly scoped, bimodal result driven by a rightmost-leaf hotspot. A matched pure-hit control returns to the coverage regime. We additionally show that physical page reordering does not translate into end-to-end wins, and that the small offset-ordered structural heuristic \texttt{Skel-5}, distinct from observed interior coverage (\texttt{Skel}), is unreliable, falling into tie or directional-toward-regression under cross-seed validation. The unreliability is specific to that small offset-order heuristic, not to interior coverage. Consequently, no single strategy stack is universally optimal: the right choice is conditional on the deployment model and the workload's hotspot structure, with interior-navigation coverage on the original layout as the robust default. Finally, the end-to-end design conclusions are established by the controlled workstation experiments. The separate-host OpenWhisk deployment provides complementary evidence that the mechanism remains deployable and that its first-query effectiveness signal is broadly consistent on a genuine FaaS runtime. The deployment covers all 65 workstation-matched cells, including 55 first-query effectiveness cells and 10 \texttt{LP} delivery-order cells. Within the 55-cell first-query domain, all 41 strong-workstation cells remain effective, and first-query effectiveness ranks correlate at Spearman $\rho\approx0.76$ to $0.81$. This is a first-query effectiveness portability result, not a cross-platform end-to-end or hardware-portability claim.

To our knowledge, this is the first work to quantify the first-query versus end-to-end trade-off in SQLite-backed serverless cold starts at OS-syscall granularity. The framework is non-intrusive, operating entirely at the application layer with standard OS interfaces, and is designed to operate within the execution constraints of FaaS and edge environments.

For future work, the page-type knowledge that drives our selection lever can be pushed below the file abstraction: NVMe Stream Directives or ZNS can physically segregate interior and leaf pages at the SSD level, achieving type-aware placement without the leaf-displacement penalty that made file-level reordering a negative result, and preventing garbage collection from perturbing layout over time. In the object-storage regime, the same skeleton-first selection maps to a VFS-level question: which pages to coalesce into a single range request, and whether to issue background read-ahead. At millisecond per-fault costs, the trade-offs we quantify become correspondingly larger. A continuous prefetch direction, maintaining hot-set residency across invocations, would extend our cold-start framework to steady-state scenarios, but this would move the design point from low-frequency, no-root application-layer operation to the high-frequency, kernel-level regime occupied by Leis et al. \cite{Leis2023}, and would require re-evaluating the deployment model accordingly. More broadly, we argue that cost accounting, not first-query latency alone, should be the evaluation standard for cold-start prefetching.
